# v0.1.5 — Diagnostics and steadier quota checks

**Draft · Unreleased.** The development version advances from 0.1.3 to 0.1.5. No v0.1.5 tag, installer or GitHub release has been created; published downloads remain at v0.1.2. The quota-checking improvements below are release goals, not completed fixes.

## Added: optional local diagnostics

- Enable diagnostic logging in **Settings → Connection & diagnostics**, Save, and use **Open logs folder** to access the recorded evidence. Logging is off by default.
- Record loading and stale episodes, refresh triggers, failures/timeouts, recovery, shared-state delivery, and webview lifecycle. Startup loading and loading after previously usable data can be investigated separately. Aggregated render counts help investigate UI activity without logging every render.
- Logs stay beside the active configuration in `diagnostics/`. Buffered, event-driven recording and rotation limit retained logs to **5 MiB per configuration folder**. Credentials, account identifiers, quota values and raw protocol responses are excluded.
- A local summary script reports episode frequency, duration statistics, incomplete observations, recurring errors and observed triggers. See the [diagnostic logging guide](diagnostic-logging-implementation-report.md) for collection, analysis and validation details.

## Planned before release: fewer unintended empty loading states

- Reduce unnecessary transitions from visible quota information to empty loading placeholders during normal use, particularly in Screen Edge and Compact HUD.
- Where account continuity is verified, aim to keep the last validated values visible and clearly marked stale while a refresh or retry completes. Preserve account boundaries: a confirmed change, sign-out or unverifiable binding must not expose previous-account values as current data.
- Make active checking, waiting for retry, and account verification easier to distinguish. Use recorded evidence to investigate refresh failures, account-update handling, state reconciliation and view recreation before selecting fixes.
- Compare runtime empty-loading episode counts and durations before and after changes. Verify fresh, stale, retry, recovery and account-boundary behavior in Overview, Edge and HUD, while preserving the existing shared scheduler and bounded missing-data policy.

These experience improvements remain **pending implementation and validation**. The [account-update investigation](account-update-empty-quota-investigation.md) records a suspected path that can clear quota values; it has not established the cause of the reported runtime occurrences. Diagnostic logging alone does not change loading behavior.

## Carried forward and release readiness

The earlier [0.1.3 development changes](v0.1.3-release-notes.md), including compact widget sizing and countdown readability, remain included. npm, Cargo, Tauri, lockfiles and packaging-check defaults now identify version 0.1.5; dependency versions are unchanged.

Diagnostic tests and synthetic native checks passed on the preceding development baseline, as recorded in the [diagnostic implementation report](diagnostic-logging-implementation-report.md). This draft does not claim that a packaged 0.1.5 build or the planned checking improvements have passed validation. The installed Tauri CLI binding issue, unresolved notification delivery, and existing manual Windows validation limits remain documented in the project reports and [README](../README.md#known-limitations).
